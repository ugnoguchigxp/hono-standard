# 実装計画 06: ページ本文の自動保存

状態: 未実装

依存: [計画 05](./plate-notion-plan-05-editor-save.md) の手動保存が完成し、保存成功・失敗・競合・離脱確認のテストが通っていること。

## ゴール

本文の最後の入力から1秒後に、自動で `PUT /api/pages/:id/content` を呼ぶ。遅い通信中も入力を続けられるようにし、古い応答で「保存済み」と表示したり、古い本文で新しい本文を上書きしたりしない。手動の「保存」ボタンは即時保存の手段として残す。

## 先に守るルール

1. 同じページの保存リクエストは常に1件だけ進行させる。TanStack Query の mutation を使うが、複数の `mutate()` を同時に発火しない。
2. 保存する本文はリクエスト開始時のスナップショットにする。送信後も編集でき、新しい入力は次の保存に回す。
3. `revision` は最後にサーバーから成功応答で確認した値だけを使う。送信前に増やさない。
4. 成功応答が返っても、その送信後に追加編集があれば「保存済み」にはしない。次の保存で最新の本文を送る。
5. `409` または通信失敗で自動再送を止める。下書きを残し、計画 05 の競合表示または「再試行」を出す。エラー状態のまま一定間隔で再送し続けない。
6. ページ ID またはユーザー ID が変わったら、前のページのタイマーと下書きを新ページへ持ち込まない。

## 小さな保存制御のモデル

`web/src/hooks/use-page-autosave.ts` に制御を置き、UI とは分ける。使う値は以下に限定する。保存状態ラベルはこれらから計算し、別の `isSaved` フラグを持たない。

| 値 | 意味 |
| --- | --- |
| `latestValue` | 画面で現在編集中の Plate JSON。サーバー応答キャッシュとは別の未保存下書き |
| `editSequence` | `onChange` が本文を変更するたびに増える番号 |
| `savedSequence` | サーバーが保存成功を返した本文の番号 |
| `confirmedRevision` | 最後の GET または PUT 成功応答で確認した revision |
| `inFlight` | 現在の1件の保存スナップショット、送信時の `editSequence`、Promise |
| `timer` | 最後の入力から1秒を測るタイマー。ページ切替やアンマウント時に破棄する |

`editSequence > savedSequence` なら未保存。`inFlight` があれば「保存中」。失敗・競合は mutation の結果を表示する。表示の優先順位は「競合」→「保存失敗」→「保存中」→「未保存」→「保存済み」。保存中でも編集が増えれば、成功後に「未保存」へ戻る。

## 保存の順序

1. `PageEditor.onChange` で `latestValue` と `editSequence` を更新し、既存タイマーを取り消して1秒タイマーを作る。選択位置だけの変更では起動しない。
2. タイマーが発火した時、未保存がなく、保存中でなく、失敗・競合でもなければ、`latestValue` と `editSequence` を固定して PUT を1件送る。保存中なら新しいリクエストを作らず、最新値だけ保持する。
3. PUT 成功時は応答の `revision` を `confirmedRevision` にし、送信時の番号を `savedSequence` にする。query キャッシュには**その応答で確認できた本文**だけを書き込む。送信中に追加編集があった場合、画面の `latestValue` は変更しないで、新たに1秒タイマーを開始する。
4. PUT 失敗時は `latestValue` を維持する。`409` は計画 05 の競合 UI に戻し、別の revision で自動上書きしない。その他の失敗は「再試行」を表示し、押したときだけ現時点の `latestValue` を送る。
5. 「保存」ボタンはタイマーを取り消し、未保存なら同じ手順で直ちに保存する。保存中は無効にする。

計画 05 では保存中にエディタを読み取り専用にしたが、この計画ではそれを外す。代わりに上の単一リクエストと連番で古い応答を扱う。TanStack Query の mutation を並列実行するだけでは順序を保証できないので、その方法にしない。[TanStack Query の mutation scope](https://tanstack.com/query/latest/docs/framework/react/guides/mutations) は直列化できるが、古い revision の送信を自動調整しないため、この計画では「同時に1件だけ起動する」制御を使う。

## 画面と離脱

`web/src/views/pages-view.tsx` は計画 05 の状態表示を使い続ける。未保存・保存失敗・競合ではページ切替・ログアウト時の破棄確認を残す。保存中は完了まで離脱とログアウトを無効にする。タブを閉じる・再読み込みする際は、未保存または保存中ならブラウザーの標準確認を出す。タイマー待ちの状態は「未保存」であり、「保存済み」と表示しない。

計画 05 の手動保存で確認した query key `['pages', userId, 'detail', pageId]` をそのまま使う。編集中の query が再取得されても、未保存の `latestValue` を GET 応答で上書きしない。別タブの変更は PUT の `409` で検出する。ページ切替時はタイマーを止めるが、未保存の破棄は計画 05 の確認を通った場合だけにする。

## 実装順序

1. `git status --short --branch`、`bun run typecheck`、`bun run test` で変更前の状態を記録し、計画 05 の実装とテストを確認する。未実装なら仮の保存関数を作らず、依存不足を報告する。
2. `web/src/hooks/use-page-autosave.ts` に、1秒タイマー、最新下書き、連番、単一の PUT を実装する。`web/src/hooks/use-page-autosave.test.ts` でタイマーと遅い応答を先に検証する。
3. `web/src/views/pages-view.tsx` の手動保存制御をこの hook へ移す。二つの保存経路を並立させず、保存ボタンも同じ hook の即時保存を呼ぶ。
4. `PageEditor` の保存中 `readOnly` を外す。離脱・ログアウトの防止は残す。計画 05 の関連 UI テストを更新する。
5. `web/src/api.ts` の query キャッシュ更新が、成功した本文だけを保存していることを確認する。新しい API や DB migration は追加しない。

## 必須テスト

| ケース | 合格条件 |
| --- | --- |
| 1回入力して999 ms | PUT は0件。「未保存」 |
| さらに1 ms | PUT は1件。送信中は「保存中」 |
| 入力を続ける | タイマーが延び、最後の入力から1秒後に最新値を送る |
| PUT が遅い間に追加編集 | 2件を並列送信せず、最初の成功後も「保存済み」にならず、最新値を次に送る |
| 最初の PUT が成功 | revision が1だけ進み、応答した本文だけがキャッシュに入る |
| ネットワーク失敗 | 下書きを残し、自動再送しない。「再試行」で最新値を送る |
| `409` | 下書きを残し、自動上書きしない。計画 05 の競合 UI が出る |
| タイマー待ちでページ切替・ログアウト | 破棄確認なしに内容を失わない |
| ページ A から B へ移動 | A のタイマーや遅い応答で B を書き換えない |

テストには fake timer と遅延 Promise を使い、実時間の sleep を使わない。状態ラベルと PUT の回数・本文・revision を検証する。

## 検証と完了報告

順に `bun run test -- web/src/hooks/use-page-autosave.test.ts web/src/views/pages-view.test.tsx web/src/api.test.ts`、`bun run typecheck`、`bun run lint`、`bun run format:check`、`bun run build:web`、`bun run verify`、`git diff --check` を実行する。すべてエラーなしを合格とする。ブラウザーでも入力→待機→保存→再読み込み、通信を遅くした連続入力、オフラインでの失敗表示を確認する。失敗時は対象を直して対象テストから再実行し、最後に全体ゲートを通す。

完了報告には変更ファイル、自動保存の待機時間、通信中の編集・失敗・競合の確認結果、未確認事項を記載する。

## 非目標

オフライン同期、強制終了後の下書き復元、複数端末の自動マージ、スラッシュメニュー、リスト、AI 機能は含めない。DB schema と API 契約も変更しない。
