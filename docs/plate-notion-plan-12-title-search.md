## 目的と選定理由

ページ数が増えても、タイトルの一部から本人のページを見つけ、保存内容を失わず開けるようにする。[全体コンセプト](./plate-notion-concept.md)の体験の中心「ページを検索し」と段階2「検索」、[要件対応表](./plate-notion-requirements-coverage.md)の12候補を具体化する。

11のゴミ箱に続き、通常の有効ページだけを探す導線を作る。本文検索はJSONからのテキスト抽出・索引・形式移行を伴うため分離する。タイトル検索は既存pages.titleで実現でき、本文schemaやPlateを変更しない。

## 範囲・非目標

対象は本人の未削除ページの保存済みタイトルを検索するAPI、サイドバーの検索ダイアログ、結果から既存ページ詳細へ移動する操作。部分一致・検索結果の追加読み込み・同名識別・未保存離脱保護を含む。

本文検索、全文索引/FTS、曖昧検索、語分割・複数語AND/OR、検索ランキング、ゴミ箱検索、履歴検索、DB列検索、他ユーザー/公開ページ検索、検索履歴の保存、AI検索、URLでの検索共有は対象外。未保存タイトルは検索対象にしない。検索語をページ本文・DB・localStorageへ保存しない。

## 検索文字列と一致規則

入力qを共有schemaでtrimし、1〜200 UTF-16コード単位とする。空白のみはAPIで400、UIでは「タイトルを入力してください」と表示して通信しない。空欄を全件一覧として返さない。中間の空白は保持し、文字列全体を一つの部分一致語として扱う。

ASCII英字だけ大小を区別しない。日本語・全角半角・ひらがな/カタカナ・アクセント付き文字・Unicode正規化は変換せず文字どおり照合する。例: `Memo` は `memo` に一致、`会議` は `週次会議メモ` に一致、`会 議` は `会議` に一致しない。`％` と `%` は別文字。

`%`、`_`、引用符、バックスラッシュは普通の文字として検索する。検索パターン演算子にしない。SQLはバインド変数を使い、`instr(lower(title), lower(q)) > 0` 相当のASCII大小無視の部分一致で実装する。qをSQL文字列へ補間しない。SQLiteのlowerと同じASCIIだけの正規化を共有関数で定義し、JavaScriptのUnicode全体のtoLowerCaseで異なる一致規則を導入しない。

API/キャッシュ/cursorが使う正規化qはtrim後のASCII小文字化。入力欄には利用者の入力をそのまま表示し、正規化のためにカーソル位置やIME入力を変えない。

## UI 契約

1. サイドバーに「ページを検索」ボタンを置く。ログイン済みの `/pages`、ページ詳細、11のゴミ箱で利用可能。グローバルショートカットは追加しない。
2. 検索ダイアログは本文エディタをunmountせず重ねて開く。本文/タイトルが未保存・失敗・競合でも検索だけは利用可能。送信中のページ操作やログアウト保護を迂回しない。
3. 入力にラベル「タイトルを検索」、ダイアログに見出し・aria-modal・フォーカス保持を付ける。開いたら検索入力へフォーカス、Escape/閉じるで検索だけを閉じて元のフォーカスへ戻す。既存未保存確認と同時にEscapeを取り合わない。
4. 入力が最後に変わってから300ms後に検索。IME変換中は送信せず、変換確定後に待機開始。空白のみはタイマー/進行中検索をcancelして結果を隠す。不正長なら入力エラーを表示し送信しない。
5. 新しい語へ変わった瞬間に前の結果を選べない状態にする。語ごとのキャッシュは利用してよいが、現在の正規化語と一致する結果だけを表示する。旧応答を最新語の結果へ混ぜない。
6. 「検索中」「該当するページはありません」「検索できませんでした」と再試行を区別し、件数や読み込みをaria-liveで伝える。ネットワーク失敗を0件扱いしない。
7. 結果はタイトル・親の表示を持つ。既存本人一覧から祖先パスを構築し、同名はパスで区別。パスも同じ場合は安定IDの識別ラベルを加える。親情報が未取得ならタイトルと識別ラベルだけで操作可能にし、見えない親を別APIで勝手に取得しない。visited Setで循環を止める。
8. 結果項目はアクセシブルなボタンとし、Tab/Shift+Tab・Enter/Spaceで選択する。複雑なcombobox/listbox独自キーボード仕様は追加しない。「さらに表示」で次の20件を読む。
9. 保存中・移動/複製/削除/復元中は結果選択を無効にする。未保存・失敗・競合時は選択意図を保持して既存破棄確認を表示。戻るなら検索へ戻り、下書きを保持。破棄を明示したときだけページを移る。
10. 選択中と同じpageIdならダイアログを閉じるだけで、詳細再取得やエディタ再初期化・下書き破棄をしない。別IDなら通常の `/pages/$pageId` へ遷移し、既存詳細GETで本文を読む。検索応答を詳細データとして合成しない。
11. 一覧が利用可能なら選択先の祖先を展開する。検索結果の存在だけで一覧へ仮ページを挿入しない。検索後に削除された先が404なら通常の「ページが見つかりません」と再検索手段を表示し、別ページを自動選択しない。

未保存確認を出す前に検索ダイアログを一時非表示にする等、フォーカストラップを同時に二つ作らない。キャンセルで検索語・結果位置を戻せるようにする。同じユーザー/ページで検索を閉じる場合は語を保持してもよいが、セッション変更・ページ領域のunmountでは破棄する。

## API と共有データ契約

`GET /api/pages/search?q=会議&limit=20&cursor=...` を既存の本人認証配下に追加する。`/search` は `/:id` のUUID検証より前に登録し、11の `/trash` との両方をテストする。既存 `/api/pages` の全件一覧契約は変更しない。

| query | 契約 |
| --- | --- |
| q | 必須、trim・ASCII小文字化後1〜200文字 |
| limit | 省略時20、10進の整数文字列1〜50。空文字・小数・負数・指数表記を拒否 |
| cursor | 省略可、空文字不可、最大1024文字。base64urlでエンコードしたcursor |

未知queryと同じキーの重複指定は400。ownerId/includeDeleted等は受け付けない。GET bodyを利用しない。

```ts
type SearchPagesResponse = {
  query: string; // 正規化q
  pages: PageSummary[];
  nextCursor: string | null;
};
```

成功200、0件も同じ形。ownerId・本文・削除単位・本文revision・総件数を返さない。全ページ総数や他人の一致件数を漏らさない。ページ配列はlimit以下、cursor有無はlimit+1件の取得で決める。

`shared/schemas/page-search.schema.ts`（新規）にquery、response、cursor内部構造と型を置き、PageSummaryを再利用する。cursorは `{ v: 1, query: 正規化q, createdAt: ISO UTC日時, id: UUID }` の固定形式。decode後のstrict検証、バージョン、q一致、Date/DB精度との整合を確認する。現在のtimestampは秒精度なのでcursorの日時もDBの実値をそのままISOへ変換し、独自のミリ秒丸めを加えない。

不正cursor、別qのcursor、未知versionは400 `{ message: "Invalid request" }`。cursorは署名/認可tokenではない。改変された有効cursorが入力されても、必ずownerId・deletedAt条件を再適用する。cursorの参照行を取得して認可判定する方式にせず、境界値として使う。前ページ末尾行が削除されても次ページを取得可能にする。

## DB・サービス・migration

`searchPages(ownerId, input)` を既存pages serviceまたは隣接するread専用factoryに追加する。ownerIdは認証から明示的に渡し、client.readを利用する。

検索WHEREは `owner_id=本人 AND deleted_at IS NULL AND タイトル部分一致`。cursor指定時は `(created_at > cursor.createdAt) OR (created_at = cursor.createdAt AND id > cursor.id)` を同じWHEREへ加える。ORDER BY createdAt ASC, id ASC。ランキングやupdatedAt順を使わない。改名・本文保存で順序が頻繁に変わらないよう既存一覧と揃える。

SQLで絞り込み・limit+1取得し、全件や他人のページを読んでJavaScriptでfilterしない。本文テーブルやゴミ箱履歴をjoinしない。11の不変条件を前提に、有効な子孫は有効祖先を持つ。破損データ修復を検索の副作用で行わない。

既存owner/parent索引および11のowner/deletedAt索引を利用できるが、中間部分一致は一般のtitle B-treeでは高速化できない。今回は新列・FTS・索引・migrationなし。実装時の測定で必要となった追加索引は別判断として報告し、設計根拠なくmigrationを増やさない。

検索は保存データを書き換えない。revision・updatedAt・ID・operation receiptsを変更しない。GETだからといってアクセス回数をDBへ保存する機能を加えない。

## キャッシュ・更新・並行変更

`web/src/api.ts` にfetchPageSearchとusePageSearchQueryを追加する。追加読み込みはTanStackのinfinite queryを利用し、キーは `['pages', userId, 'search', normalizedQuery, limit]`、initialPageParamはcursorなし、次はnextCursor。queryFnへAbortSignalを渡す。未ログイン・空入力・ダイアログ非表示では起動しない。自動retryは無効、明示再試行を出す。

検索結果はqueryキャッシュを正本とし、グローバルstateへ全件コピーしない。pageIdで表示を重複排除し、limitより多いページを無制限にプリフェッチしない。先頭ページ再取得時は追加ページの古いcursor列をリセットし、先頭から読み直す。「さらに表示」送信中は同じ次ページを重複取得しない。

通常一覧/詳細のmutation成功に合わせて本人のsearch配下もinvalidateする。08改名、09移動、10作成/複製、11削除/復元、01通常作成が対象。本文保存は検索タイトルを変えないため検索再取得を追加しない。invalidateによるリセットは未保存本文/タイトルを変更しない。

既存setSessionUserのpages配下cancel/removeに検索も含める。最新のセッション世代境界を使い、旧ユーザーの遅延応答・検索選択意図・下書き確認を新セッションへ持ち込まない。検索qや結果を構造化ログへ追加しない。URLのqueryは既存アクセスログ/プロキシで記録され得るため、将来実データ運用で必要なら検索語のログ除外方針を確認する。

ページングは一回のSQL内で整合した結果を返すが、複数HTTP要求を跨ぐsnapshotは保証しない。途中で改名/作成/削除があれば結果数は変わる。古い境界以前で一致した行は先頭再検索まで出ない場合がある。この制約を隠して全件一致を保証しない。「再検索」は追加ページを捨て先頭から取得する。検索は書込みしないため409や更新revisionを新設しない。

結果取得後の削除・移動・改名は、開いた先の通常GETと認可が最終判断。ゴミ箱移動中/復元中の状態を検索結果だけで上書きしない。同タブ11削除成功では対象IDをsearchキャッシュから外し、再取得。別タブ削除は次GET/再検索で検出する。

## エラー・データ保持

| 状況 | 挙動 |
| --- | --- |
| 空入力・長さ超過 | 入力案内/エラー、通信なし。API直接指定は400 |
| query/cursor不正 | 400。正常な別条件へ黙って置き換えない |
| ネットワーク・500 | 入力と元の本文下書きを保持、再試行。0件表示に変えない |
| 次ページ取得失敗 | 取得済み結果を保持、次ページだけ明示再試行 |
| cursor仕様が変わった等で次ページ400 | 「検索結果を更新してください」と先頭再検索。自動で別qを送らない |
| 401 | 既存認証失効処理、旧検索キャッシュを除去 |
| 結果を開いて404 | 元の検索へ戻る/再検索可能。別ページへ自動移動しない |
| 未保存の離脱をキャンセル | 本文/タイトル下書きを維持、検索結果へ戻す |
| 保存中に選択 | 遷移を開始せず、完了後の明示選択を待つ |
