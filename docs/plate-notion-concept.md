# Plate を使った Notion 風アプリのコンセプト

作成日: 2026-09-30

状態: 実装前の設計案

## 目的

ページを自由に書き、階層で整理し、必要に応じて同じ情報をデータベースの複数のビューから扱える Web アプリを作る。まずは Notion の非 AI 機能を参考に、日常的な文書作成と情報整理が成立する体験を実現する。AI 機能は別の設計課題とし、この文書では仕様を決めない。

## 体験の中心

1. ログインするとサイドバーに自分のページ階層が表示される。
2. ページを開くと、タイトル、アイコン、本文をその場で編集できる。本文はブロック単位で操作し、`/` で種類を選べる。
3. 編集は自動保存され、再読み込みや別端末からのアクセス後も内容が残る。保存状態と失敗は明示する。
4. ページを検索し、リンクで結び、サイドバーから移動・複製・削除できる。
5. 表形式が必要な情報はデータベースに保存し、同じレコードをテーブルやボードなどのビューで見る。各レコードは本文を持つページでもある。

## 基本方針

| 関心事 | 方針 |
| --- | --- |
| 本文編集 | React 上の Plate を使用する。標準プラグインを組み合わせ、必要なブロックだけを有効にする。 |
| 正本 | ページ本文は Plate の構造化 JSON をサーバーに保存する。Markdown は入出力形式とし、唯一の保存形式にはしない。 |
| ページとデータベース | ページ階層、権限、データベースの行・列・ビューはアプリ固有のドメインとして API と DB で管理する。エディタの内部データに埋め込まない。 |
| 既存基盤 | `web/src` の React と TanStack Router/Query、`api` の Hono、`shared/schemas` の Zod、Drizzle + SQLite、既存の認証を使う。 |
| 拡張性 | ページ ID とブロック ID を安定させ、リンク、コメント、履歴、共同編集を後から関連付けられるようにする。 |

Plate は見出しやリストなどの基本ブロック、スラッシュメニュー、ドラッグ操作、Markdown 変換、Yjs 連携などをプラグインとして提供している。ただし、**Notion のページ管理やデータベース全体を提供する製品ではない**。その境界をアプリ側の責務として扱う。Plate の API・依存パッケージは実装開始時に採用バージョンで再確認する。

## 構成案

```text
React UI
  サイドバー / 検索 / ページ画面 / データベースビュー
       │
       ├─ Plate: ページ本文の編集・ブロック操作
       │
       └─ TanStack Query: 読み込み・保存状態・キャッシュ
                         │
                    Hono API
                         │
              認可 / 入力検証 / 更新競合の判定
                         │
                Drizzle + SQLite
              ページ / 本文 / プロパティ / ビュー
```

### データの境界

- `pages`: ID、親ページ ID、タイトル、アイコン、カバー、並び順、作成者、作成・更新日時、削除日時を持つ。親子関係と順序は本文 JSON とは別に保存する。
- `page_contents`: ページ ID、Plate JSON、リビジョンを持つ。サーバーでノード種類・サイズ・深さを検証する。本文内のページリンクやメディア参照は安定 ID で保持する。
- `databases`: ページとの関連と、列定義を持つ。`database_items` の各行は `pages` のページを参照し、本文を編集できる。
- `database_properties` / `database_item_values`: 列の種類・設定と、行ごとの値を分ける。最初はテキスト、数値、選択、ステータス、日付、チェックボックスを対象にする。
- `database_views`: 表示形式、表示列、フィルター、ソート、グループを保存する。ビューはデータのコピーではなく、同じ行への表示設定とする。
- 添付ファイルは JSON や SQLite の BLOB に直接置かず、アプリが管理するファイルストレージに保存し、DB には参照とメタデータを置く。保存先・容量制限・バックアップ方法は添付実装時に決める。

これは論理モデルであり、具体的なテーブル名・制約・インデックスは最初の縦断機能を実装する際に確定する。

### 保存と競合

編集はクライアントで短く間引いて送信する。サーバーはページごとのリビジョンを照合し、一致した更新だけ保存して新しいリビジョンを返す。通信失敗時は未保存状態と再試行手段を表示し、内容を黙って破棄しない。古いリビジョンでの更新は上書きせず競合として扱う。最初の段階は単一編集者を想定し、競合解決 UI を含む共同編集は後の段階で設計する。

本文保存とタイトル・階層変更は別 API に分ける。移動・削除・権限変更はサーバー側で認可し、子ページやデータベース行への影響を明示的に扱う。

## 機能の段階

| 段階 | 実装するもの | 完了の目安 |
| --- | --- | --- |
| 1. ページの縦断機能 | 認証済みユーザーのページ作成、一覧、階層、タイトル変更、Plate 本文、基本ブロック、`/` メニュー、自動保存、再読込 | ページを作成して編集し、ブラウザー再起動後に同じ内容と並びを復元できる。 |
| 2. 整理と再利用 | ページ移動・複製・ゴミ箱、検索、ページリンク、アイコン・カバー、テンプレート、Markdown 入出力 | ページ数が増えても見つけ、整理し、再利用できる。 |
| 3. データベース | 行をページとして扱うモデル、基本プロパティ、テーブル、フィルター・ソート、ボード・カレンダー・リスト・ギャラリー | 同じレコードを複数ビューで編集し、値が一貫する。 |
| 4. 共同作業と公開 | ワークスペース、ページ権限、招待、コメント・メンション、通知、履歴、公開リンク | 権限に応じて安全に閲覧・編集でき、変更を追える。 |
| 5. 高度な機能 | リレーション・ロールアップ・数式、タイムライン・チャート・フォーム、ボタン・自動化、リアルタイム共同編集、オフライン、外部 API | 個別の利用場面を定めて順次追加する。 |

段階は優先順位の案であり、Notion の全機能を同時に再現する約束ではない。最初に段階 1 の縦断機能を完成させ、操作感と保存の信頼性を確認する。

## 初期スコープと非目標

初期実装は、既存の認証を使う単一ユーザー向けページ編集に絞る。既存の認証方式、既存 API の契約、テンプレートの他ブランチは変更しない。Plate と必要な UI 依存は採用するが、データベース製品や同期基盤の追加は段階 1 の要件にしない。

AI の文章生成・検索・議事録・エージェント、Notion Mail/Calendar 相当の別製品、リアルタイム共同編集、オフライン同期は初期実装の対象外とする。AI を後で加える際は、ページ・ブロックへのアクセス権と編集履歴を共通の境界として利用し、AI 独自の体験を別途設計する。

## 実装時に決めること

1. Plate の採用バージョンと、最初に有効化するブロック・UI コンポーネントの具体的な組み合わせ。
2. ページの所有単位を当面ユーザーにするか、初期からワークスペースを導入するか。将来の共有を考慮し、所有者 ID は明示的に持つ。
3. JSON スキーマのバージョン管理と、Plate の更新時に保存済み本文をどう移行するか。
4. 添付ファイルの保存先と、公開ページを導入する際のアクセス制御。
5. データベースのフィルター・数式をどこまでサーバーで評価するか。件数が増えてもビュー間で結果が一致する方式を選ぶ。

## 検証方針

段階 1 では、ページ作成→編集→保存→再読込、親子移動、認可外アクセス、保存失敗、古いリビジョンによる競合を対象に API と UI のテストを作る。実装後は `bun run typecheck`、`bun run lint`、`bun run test`、`bun run build:web` を実行し、すべてエラーなしを成功条件とする。既存の全体ゲート `bun run verify` も通す。失敗時は対象の実装またはテストを修正して再実行し、環境起因で実行できない場合は未検証項目として報告する。
