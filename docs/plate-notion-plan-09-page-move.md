# 実装計画 09: ページの親変更とルートへの移動

状態: 未実装。2026-09-30 に設計書のみ作成。

依存: [計画 01](./plate-notion-plan-01-pages-api.md) のページ API・認可、[計画 02](./plate-notion-plan-02-sidebar.md) の階層表示、[計画 05](./plate-notion-plan-05-editor-save.md)・[計画 06](./plate-notion-plan-06-autosave.md) の保存と離脱保護。[計画 08](./plate-notion-plan-08-title-edit.md) のタイトル状態合算との統合は、08 の最新実装を確認してから行う。

## 目的と選定理由

作成済みページを別ページの配下、または階層の最上位へ移せるようにする。ページ ID・本文・子孫を保持し、再読み込み後も新しい階層を復元する。

[全体コンセプト](./plate-notion-concept.md) の段階 2「整理と再利用」は「ページ移動・複製・ゴミ箱」から始まる。計画 01〜08 はページ作成、階層表示、本文編集・保存、スラッシュメニュー、タイトル変更を扱っているが、作成後の親変更を扱っていない。09 は段階 2 の最初の整理機能を小さく縦断実装する計画とする。

親変更は既存の `pages.parent_id` を利用でき、本文ノード追加やファイルストレージを必要としない。複製・ゴミ箱は子孫のコピーや復元単位を別途決める必要があるため、今回は混ぜない。段階 1 の未完了部分・既存不具合は先行担当者が扱い、09 に再実装を含めない。

## 範囲と対象外

対象は、ログイン済みユーザーが現在選択している自分のページの親変更。移動先は本人の未削除ページまたはルート。子孫は移動元ページへの参照を維持するため、まとめて新しい位置へ移る。

対象外は兄弟の並べ替え、`sortOrder`、ドラッグ操作、複数ページの一括移動、別ユーザー・ワークスペースへの移動、複製、削除・復元、検索、ページリンク、アイコン・カバー、DB 行、共有・AI 機能。既存タイトル PATCH の入力を親変更まで拡張しない。

09 は実装計画の連番であり、Space 課題表の 009（認証なしテンプレート問題）とは別件。Space 008 の後続機能分割のうち「ページ移動」だけを具体化する。

## UI 契約

1. サイドバーに、現在選択中のページに対する「ページを移動」ボタンを追加する。`/pages` の未選択状態には表示しない。詳細と一覧が正常に取得できたときだけ利用可能にする。
2. 本文またはタイトルが未保存・保存失敗・競合・送信中ならボタンを無効にし、「変更を保存するか取り消してから移動してください」と説明する。09 の操作を理由に下書きを破棄したり、保存を強制実行したりしない。
3. ダイアログの見出しは「ページを移動」。移動元のタイトルと現在の親を表示し、移動先を必須選択とする。選択肢に「最上位」を置き、値は `null`。ページの選択値は UUID とする。
4. 移動先は取得済み一覧から構築する。移動元自身とその子孫を除外する。同名ページは祖先を含む表示パスで区別し、パスまで同一の場合は安定した ID の識別表示を加える。表示ラベルを ID として使用しない。
5. 現在の親を初期選択する。同じ親のままなら「移動する」は無効。ダイアログを開くためだけの通信や仮ページ作成はしない。
6. ダイアログは移動先選択、エラー、「移動する」「キャンセル」を持つ。フォーカスを内部に保ち、送信前は Escape で閉じ、閉じた後は起動ボタンへ戻す。適切な `role="dialog"`、`aria-modal`、見出し・入力のラベルを付ける。
7. ダイアログ表示中は現在ページの本文・タイトル編集を一時的に無効にする。開く直前と送信直前に保存状態を再確認し、途中で未保存・送信中となったら移動を送らない。自動保存の state・revision は変更しない。
8. 送信中は移動先変更・再送・キャンセルを無効にし、選択ページ切替・作成・ログアウトを保護する。再読み込み・タブを閉じる際にも既存の保存中と同様の標準確認を出す。
9. 成功後はダイアログを閉じ、新しい親とその祖先を展開する。移動元の選択 ID・URL・本文エディタを維持する。子孫の展開状態も保持する。ルート・兄弟の順序は従来の `createdAt`、同時刻は `id` 昇順を維持する。「末尾へ移動」という意味にはしない。
10. 移動自体が成功し、一覧再取得だけが失敗した場合は「移動しました。一覧を更新できませんでした」と再取得手段を表示する。移動 POST を再送しない。

移動先の選択はこのダイアログだけの一時 state。本文やタイトルの下書きとは別にし、送信前のキャンセルで破棄できる。

ダイアログの状態は userId・セッション世代・移動元 pageId に紐付ける。送信前にページやユーザーが切り替わった場合は閉じ、前ページの移動先を次ページへ持ち込まない。候補の子孫・祖先走査にも訪問済み ID を持ち、不正な階層を検出した場合は候補を生成し続けずエラー表示して移動を止める。

## API・共有スキーマ契約

`POST /api/pages/:id/move` を追加する。既存の `/api/pages` 認証 middleware を利用し、認証コンテキストから ownerId を決定する。既存改名 PATCH、本文 PUT、GET の形式は維持する。

```json
{
  "parentId": "123e4567-e89b-42d3-a456-426614174000",
  "expectedParentId": null
}
```

上例は最上位のページを指定したUUIDの配下へ移す入力。parentId は移動先、expectedParentId は利用者が確認した移動前の親を表し、最上位は JSON null とする。両フィールドを必須とする strict object。UUID または null 以外、未知のキー、ownerId、title、revision は拒否する。

| 結果 | 応答 |
| --- | --- |
| 移動成功 | `200 { "page": Page }`。既存 `updatePageResponseSchema` と同じ形 |
| 未ログイン | `401`。既存認証契約 |
| 不正な ID・JSON、未知のキー | `400 { "message": "Invalid request" }` |
| 移動元・移動先が不存在、他人のページ、削除済み | `404 { "message": "Not found" }`。他人の存在情報を返さない |
| 自身または子孫の配下を指定 | `409 { "message": "Invalid page hierarchy", "code": "INVALID_PAGE_HIERARCHY" }` |
| 移動元の現在の親と expectedParentId が不一致 | `409 { "message": "Page parent conflict", "code": "PAGE_PARENT_CONFLICT", "currentParentId": UUIDまたはnull }` |
| DB 内の祖先参照の破損・既存循環、内部書込失敗 | `500 { "message": "Internal server error" }`。変更なし |

`shared/schemas/pages.schema.ts` に `movePageInputSchema` / `MovePageInput`、2 種類の 409 応答スキーマと型を追加する。成功型は既存 `UpdatePageResponse` を再利用してよい。クライアントは status と検証済み code で失敗を分類し、message の文字列比較で分岐しない。想定外・不正な 409 応答は一般の HTTP エラーとして扱う。

現在の親と移動先が同じで、expectedParentId も一致している場合は 200 で現在の Page を返す。DB 書き込みと updatedAt 更新を行わない。古い expectedParentId のリクエストは、移動先が現在の親と同じでも 409 にする。

## DB・サービスの更新手順と不変条件

`movePage(ownerId, pageId, input): Promise<Page>` を既存サービスへ追加する。すべての判定と更新を `client.write.execute()` 内の同一トランザクションで行う。UI の候補除外を認可・循環防止の代わりにしない。

1. 移動元を ownerId と `deletedAt IS NULL` で取得する。なければ 404。
2. 移動先が null 以外なら同じ所有者・未削除条件で取得する。なければ 404。存在確認を expectedParentId の競合応答より先に行い、他人の移動先に関する情報を返さない。
3. 移動元の現在の parentId と expectedParentId を比較し、不一致なら親競合の 409。本文 revision・updatedAt は比較に使用しない。
4. 同じ親への指定なら現在の Page を返す。それ以外は、移動先から親方向へ辿り、移動元に到達したら階層不正の 409。自身への移動も同じ扱いとする。
5. 祖先走査では訪問済み ID の Set を持つ。移動元以外の循環、存在しない・削除済み・別所有者の祖先を見つけたら、内部整合性の問題として 500 とし、書き込まない。各祖先取得にも所有者条件を付ける。終端は parentId=null。
6. 移動元1件の parentId と updatedAt のみを更新する。WHERE に移動元 ID・ownerId・未削除・expectedParentId を含め、null 比較には `IS NULL` を使う。更新件数が1件であることを確認する。
7. 件数0の場合は同じトランザクション内で再確認し、不存在なら404、親不一致なら409、それ以外は500。返却する Page は更新後の行から生成する。

子・孫の parentId、title、ownerId、createdAt、updatedAt と、全 `page_contents` の valueJson・revision・updatedAt は変更しない。子孫は移動元の ID に接続したまま移動する。ページや本文の新規作成・削除をしない。

移動先の祖先が別のリクエストで変更された場合も、トランザクション内の最新状態で循環を検証する。単一 writer の外で検証してから書き込まない。並行した A→B と B→A は両方成功して循環を作ってはならない。

## フロントエンドとキャッシュ

`web/src/api.ts` に `movePage(pageId, input)` と `useMovePageMutation(userId, pageId)` を追加する。mutation の自動 retry は無効とする。使用する query key は従来どおり。

- 一覧: `['pages', userId, 'list']`
- 詳細: `['pages', userId, 'detail', pageId]`

成功時は、開始前から進行している対象 GET をキャンセルしたうえで、関数形式のキャッシュ更新で移動元の parentId だけを応答値に反映する。古い Page オブジェクトでキャッシュ全体を置き換えない。title、content、revision、他ページ・子孫のデータを保持する。存在しない詳細キャッシュを不完全なオブジェクトで生成しない。

一覧と詳細を invalidate して最新の title・updatedAt 等を再取得する。移動成功と再取得失敗は分けて扱う。キャッシュの失敗を理由に移動成功を取り消す表示にはしない。移動前の楽観的なツリー変更は行わない。

08 と既存セッション管理が採用したセッション世代の境界を再利用する。ユーザー変更やログアウト・再ログインの後に届く旧 mutation 応答でキャッシュを復活させない。本人に対する二つの移動操作を同時に開始させず、送信中の操作元 ID とセッションを固定する。

`PagesView` に移動ダイアログ・送信状態を置く場合は、移動元となる選択中ページの `PageDocument` へ渡し、08 の単一の guard 登録箇所で `saving = bodySaving || titleSaving || movePending` とする。ページ画面側の blocker と beforeunload も同じ状態を使う。本文自動保存の判定は bodySaving のまま維持する。異なる部品から同じ guard を上書きする新しい登録を作らない。未選択状態では移動できないため、空画面用の移動 guard は不要。

ダイアログ表示中の編集停止は表示用の props で渡し、本文セッションの key や editorGeneration を変更しない。移動成功・一覧更新によるエディタの再マウントを避ける。

## 失敗・競合時の振る舞い

| 状況 | UI の扱い |
| --- | --- |
| 通信失敗・500 | 選択した移動先を残し、自動再送しない。移動が完了した可能性を説明し、「状態を確認」を表示 |
| 状態確認の GET が成功 | 最新一覧・詳細で親を確認する。希望先なら「現在この場所にあります」として閉じられる。異なる親なら最新の親を表示し、利用者が再度「移動する」を押したときだけ最新 expectedParentId で送信 |
| 状態確認が失敗 | 選択とエラーを保持し、確認を再試行できる。根拠なく expectedParentId を更新しない |
| 親競合 409 | 「別の場所でページが移動されています」と表示し、一覧・詳細の再取得を明示操作で行う。サーバー値で自動再送しない |
| 階層不正 409 | 「自分自身や子ページの中には移動できません」と表示。候補を更新して別の移動先を選べるようにする |
| 404 | 「ページまたは移動先が見つかりません」と表示。最新状態の確認へ誘導し、成功扱いにしない |
| 401・セッション失効 | 既存認証処理へ委ねる。旧ユーザーの選択・キャッシュを次セッションへ持ち込まない |

確認 GET は本文・タイトルの下書きを破棄する操作ではない。送信に入る時点では保存済みであるが、競合・再取得時も既存の下書き保護を迂回しない。送信終了後のエラー画面はキャンセル可能とする。

## 必須テストと受け入れ基準

| ケース | 合格条件 |
| --- | --- |
| root A を B 配下へ移動 | 200。A.parentId=B、一覧・詳細・再読み込みで一致 |
| 子ページを最上位へ移動 | parentId=null、元の親から外れ、選択URLは維持 |
| 子・孫付きページを移動 | 移動元1件だけ親変更。子孫のID・親参照・本文・revisionは不変 |
| 同じ親指定 | 200、updatedAtとDB状態は不変 |
| 自分・子・孫を移動先に指定 | 409階層不正、全DB状態は不変 |
| 他人・不存在・削除済みの移動元/先 | 同じ404、書込みなし。未ログインは401 |
| 不正UUID、キー省略、余分なキー | 400、書込みなし。nullは受理 |
| 古い expectedParentId | 409親競合、現在の親を上書きしない |
| A→B、B→A を並行送信 | 両方成功しない。保存後も非循環 |
| 移動先の祖先が途中で変更 | 最新のトランザクション状態で判定し、循環なし |
| 既存祖先の循環・参照破損 | 500、無限ループなし、書込みなし |
| DB更新失敗 | ロールバックし、本文・階層に部分更新なし |
| 未保存タイトル/本文、保存失敗/競合 | 移動を開始せず、下書きを保持 |
| 移動先候補と同名ページ | 自分・子孫を除外し、IDで正しい候補を選択 |
| 送信中の連打・離脱・ログアウト | POST1件。保護が働き、二重操作しない |
| 成功後の表示 | 新親・祖先を展開。URL・本文エディタ・子孫状態を維持 |
| 成功後GETだけ失敗 | 移動成功と再取得失敗を区別。再取得はGETのみ |
| 通信失敗後の状態確認 | 自動再送なし。最新親を確認してから明示再実行 |
| 改名/本文保存/古いGETとの応答順逆転 | title・parentId・content・revisionを相互に消さない |
| セッション変更後の遅延応答 | 旧セッションのキャッシュを再生成しない |

API統合テストは既存方式の一時 SQLite DB・実 migration・ユーザーA/B・Hono `app.request()` を使う。書込み前後の `pages` と `page_contents` を比較し、レスポンスだけで成功判定しない。並行移動は別リクエストで実行し、DBの非循環性を確認する。祖先の破損fixtureは一時DB内に限定する。

UIは Testing Library、遅延応答は制御可能な Promise を使う。ブラウザーでルート→子→孫を作成し、改名・本文保存後に移動→再読み込みを確認する。キーボード操作、ダイアログのフォーカス、狭い画面での操作も確認する。

## 検証ゲートと報告

実装後に対象テスト、既存01〜08の回帰テスト、`bun run typecheck`、`bun run lint`、`bun run format:check`、`bun run build:web`、`bun run verify`、`git diff --check` を順に実行する。既存Playwrightに移動導線を追加し、`bun run verify:e2e` で確認する。失敗時は対象から修正・再実行し、最後に全体ゲートを通す。

[delivery-quality-gates.md](./delivery-quality-gates.md) に従う。認可・入力検証・トランザクション変更として、移動サービスの認可条件・循環判定・expectedParentId判定を除いた変異をテストが検出することを局所的に確認する。祖先取得回数と移動先選択肢生成はページ数・階層深さに依存するため、深い階層・広い一覧の代表fixtureで測定し、既存一覧表示と比較した結果を報告する。新しい診断ツールや依存を無断で追加しない。公開Delivery時のセキュリティ診断・性能予算は品質契約の該当条件で判定する。

本設計書の作成ではテスト・ビルド・DB変更を行わない。実装完了報告には変更ファイル、APIの成功・拒否・競合結果、子孫と本文の不変性、ブラウザー確認、既存並行作業との統合状況、未実行項目を記載する。

## リスク・残る判断

- expectedParentId は親変更だけの簡易競合検出。親が A→B→A と戻った履歴までは検出しない。厳密な履歴検出が必要になった時点で階層revisionを別計画にする。09で列を追加しない。
- 兄弟順序は既存の作成日時順を維持する。任意の挿入位置・並べ替えは独立した設計が必要。
- 削除済み祖先や他所有者の祖先は既存データ破損として失敗させる。修復やゴミ箱復元を移動の副作用で行わない。
- 大規模な階層のページング、検索付き移動先選択、祖先取得の一括化は測定後の判断。09は現在の全件一覧と祖先走査を基本とし、製品向け性能予算は実装検証時に確認する。
- データベース行ページの階層制約は段階3で設計する。現在は一般ページだけを対象にし、未導入のDBモデルを仮実装しない。
- 08 と Luna の修正は進行中。最終的なコンポーネントのpropsとguard集約点は、その最新成果物に合わせる。機能仕様とAPI契約は本書で固定し、既存不具合の担当範囲は広げない。
